Mysql 索引失效情况

索引失效的核心原因

数据库优化器认为使用索引的成本（如随机I/O、回表操作）高于直接进行全表扫描（顺序I/O）的成本时，就会放弃使用索引。

以下是导致索引失效的具体场景和示例（以MySQL的InnoDB引擎为例，但原理通用）：

  1. 对索引列进行运算或使用函数

当你在索引列上使用函数、计算表达式或运算时，索引无法直接使用，因为索引存储的是原始值。

失效示例：
– 假设 create_time 字段有索引
SELECT * FROM orders WHERE YEAR(create_time) = 2023; – 对字段使用函数
SELECT * FROM users WHERE age + 1 > 30; – 对字段进行计算
SELECT * FROM products WHERE price * 0.8 > 100; – 对字段进行计算

优化方案：
– 将操作转移到常量一侧
SELECT * FROM orders WHERE create_time >= ‘2023-01-01’ AND create_time < ‘2024-01-01’;
SELECT * FROM users WHERE age > 29; – 等价于 age + 1 > 30
SELECT * FROM products WHERE price > 125; – 等价于 price > 100 / 0.8

  1. 在索引列上使用 NOT (!= / <>) 或 NOT IN

NOT 操作无法有效利用索引的B+树有序结构来快速定位数据。优化器通常会认为扫描整个索引不如直接全表扫描。

失效示例：
SELECT * FROM users WHERE status != ‘active’;
SELECT * FROM orders WHERE user_id NOT IN (100, 101, 102);

优化方案：
• 考虑改写为肯定的、可范围查询的语句。如果非要使用 NOT，需通过测试 EXPLAIN 确认是否真的失效，有时在数据分布特殊的情况下优化器可能仍会选择索引。

  1. 隐式类型转换

如果查询条件中的数据类型与表中字段定义的类型不匹配，数据库会进行隐式类型转换，这相当于在字段上使用了函数。

失效示例：
– 假设 user_id 是字符串类型 varchar
SELECT * FROM users WHERE user_id = 100; – 程序传入的是数字 100

– 数据库实际执行的是：
SELECT * FROM users WHERE CAST(user_id AS UNSIGNED) = 100;

优化方案：
• 保持类型一致是根本解决办法。确保应用程序传入的参数类型与数据库字段类型完全一致。
SELECT * FROM users WHERE user_id = ‘100’; – 传入字符串

  1. 模糊查询 LIKE 以通配符 % 开头

B+树索引按照字段值的前缀组织。如果查询条件无法提供明确的前缀，索引就无法用于快速定位。

失效示例：
– 假设 name 字段有索引
SELECT * FROM users WHERE name LIKE ‘%小明%’; – 前后都有%，全失效
SELECT * FROM users WHERE name LIKE ‘%明’; – 以%开头，失效

优化方案：
– 尽量使用前缀匹配，索引有效
SELECT * FROM users WHERE name LIKE ‘小明%’;

• 如果必须进行全文搜索，应考虑使用专业的全文搜索引擎（如Elasticsearch）或数据库的全文索引（FULLTEXT Index）。

  1. 复合索引未使用最左前缀匹配原则

复合索引（联合索引）的顺序至关重要。索引 (a, b, c) 相当于建立了 (a), (a,b), (a,b,c) 三个索引。

失效示例：
假设存在一个复合索引 idx_age_city (age, city)
SELECT * FROM users WHERE city = ‘北京’; – 缺少最左列age，索引失效
SELECT * FROM users WHERE age > 20 AND city = ‘北京’; – 第一列是范围查询，第二列索引失效

优化方案：
• 创建索引时，将最常用作查询条件的列放在左边。

• 查询时，必须包含复合索引的最左列。

• 对于范围查询后的列失效问题，可以考虑调整索引顺序或使用等值查询。

  1. 使用 OR 连接条件，且前后条件并非全是索引列

如果 OR 连接的多个条件中，有一个条件涉及的列没有索引，那么数据库优化器可能会选择全表扫描，而不是使用那些局部的索引。

失效示例：
– 假设 age 有索引，但 name 没有索引
SELECT * FROM users WHERE age = 25 OR name = ‘张三’; – 可能导致全表扫描

– 即使 age 和 city 都有索引，但优化器可能合并成本高，有时也会选择全表扫描
SELECT * FROM users WHERE age = 25 OR city = ‘北京’;

优化方案：
• 考虑使用 UNION 或 UNION ALL 来拆分查询，确保每个部分都能有效利用索引。
SELECT * FROM users WHERE age = 25
UNION ALL
SELECT * FROM users WHERE name = ‘张三’; – 这条依然是全表扫，但至少第一条用了索引

• 为 OR 条件中的所有列都建立索引。

  1. 数据库优化器“判断失误”（成本估算）

有时，索引本身是可用的，但优化器基于统计信息（如表的基数、数据分布等）错误地判断全表扫描比使用索引更快。
• 数据量非常小的表，使用索引反而多一次查找开销，不如直接全表扫描。

• 索引的选择性太差（如索引列“性别”，只有‘男‘/’女‘两个值），使用索引查出一大半数据，不如直接全表扫描。

解决方案：
• 使用 FORCE INDEX 或 USE INDEX 提示（hint）强制优化器使用指定索引（需谨慎使用）。
SELECT * FROM users FORCE INDEX(index_name) WHERE age = 25;

• 执行 ANALYZE TABLE 更新表的统计信息，帮助优化器做出更准确的判断。
ANALYZE TABLE users;

总结与最佳实践

要避免索引失效，请牢记以下几点：

  1. 保持类型一致：确保查询值与列类型匹配。
  2. 左边原则：对于复合索引，查询条件必须包含最左列。
  3. 不加修饰：避免对索引列使用函数、计算和运算。
  4. 谨慎模糊：LIKE 查询尽量避免以 % 开头。
  5. 善用工具：使用 EXPLAIN 命令分析每条重要SQL的执行计划，这是判断索引是否生效的唯一金标准。查看其中的 type、key、rows 等关键字段。
