网页推流webrtc服务器并转发

基于 Go 的“网页推流 WebRTC 服务端 + 转发（WebRTC 订阅）”实现

下面给出一个可运行的最小方案：

  • 浏览器通过 WebRTC 推流（Publish） 到 Go 服务器。
  • 服务器把收到的轨道转为 TrackLocal，并支持**多个订阅端（Play）**以 WebRTC 转发。
  • 信令采用 WebSocket，纯后端+前端静态页即可跑通。
  • 依赖 pion/webrtc（Go 社区最成熟的 WebRTC 库）。

如果你还想转 RTMP/RTSP/HLS：在本文最后附了思路与示例命令（用 FFmpeg）——可以在本项目基础上很容易扩展。

架构与数据流

  • Publish（浏览器 → 服务端）

    1. 浏览器采集摄像头/麦克风流。
    2. 通过 WebSocket 发送 SDP Offer 给服务端。
    3. 服务端用 Pion 创建 PeerConnection，SetRemoteDescription，返回 Answer。
    4. 服务端在 OnTrack 收到 RTP 包，写入 TrackLocalStaticRTP，存入内存注册表（按 streamID）。

  • Play（服务端 → 浏览器）

    1. 订阅端通过 WebSocket 携带 streamID 发送 Offer。
    2. 服务端创建新的 PeerConnection，把注册表里的 TrackLocal 加到该连接。
    3. 服务端返回 Answer，建立连接后即可观看。

这相当于一个“超轻量 SFU（只转发，不混流）”。

扩展：转发到 RTMP/RTSP/HLS

思路 A（最简单）：用外部 FFmpeg 订阅播放端地址再转协议。

  • 把本服务作为“WebRTC 拉流源”，FFmpeg 侧用 whip/whep 或者浏览器不可行时，用另一段 Go/Pion 代码拉取 TrackLocal 再推给 FFmpeg。

  • 也可直接在服务端把 OnTrack 的 RTP 解码/复用后 -f flv rtmp://...。

    • 实现上可将 OnTrack 的原始 RTP 写入本地 UDP 端口，再让 FFmpeg 从该端口读：

    • 生成 video.sdp 描述 RTP 输入（含端口、payload type、codec）。也可以用 pion/rtp 直接喂给 ffmpeg 的 -f rtp stdin，但要处理时序戳。

思路 B（更工程化）：引入现成媒体服务器（如 MediaMTX / rtsp-simple-server）。

  • 在 OnTrack 时将 RTP 喂给 MediaMTX 的 RTSP 推流入口，它会自动产出 RTSP/RTMP/LL-HLS 等多协议。
  • 这样你只维护 WebRTC-In 的入口代码，协议扇出交给专业服务器。

注意事项与生产建议

  1. NAT 穿透与公网部署：浏览器端 WebRTC 强烈建议配置 TURN 服务器，否则在对称 NAT 网络下易连接失败。
  2. 多流/多分辨率：本文演示单路音视频。需要多清晰度/转码可引入 gstreamer/ffmpeg 或者服务端做 SVC/Simulcast（Pion 支持 Simulcast）。
  3. 资源管理：给每个 PeerConnection 做超时/断线清理；在 OnConnectionStateChange 检测 failed/disconnected 做注销。
  4. 带宽与拥塞控制：生产中考虑设置 RTCPFB、限制码率、定期发送 REMB/TWCC，或使用 pion 的 Interceptor 管线。
  5. 安全：上线请使用 HTTPS/WSS，并做鉴权（例如在 streamId 基础上加鉴权 Token）。
  6. 编解码：默认注册 VP8/Opus，若需 H.264 请确保浏览器与服务端都启用并且有正确的 PT/参数匹配。
